# Qogam: запрос API backend-разработчику

Дата: 6 октября 2026. Основание: `Qogam_TZ_v1.docx` и реализованный Flutter-клиент.

Привет! Мы подключили все операции текущего Swagger. Ниже полный список API,
которые нужны для реальных обращений и остальных функций по ТЗ.
Просьба согласовать контракты, добавить их в OpenAPI и предоставить staging
с тестовыми данными. Названия новых путей ниже — предложения, а не утверждение,
что они уже существуют. Если часть функций реализована под другими путями,
достаточно прислать соответствие и схемы.

## 2. Приоритеты

- **P0 — подключение текущего основного сценария:** публичные проблемы,
  карточка/история, подача, собственные обращения, повторная отправка,
  присоединение, справочники статусов, границы города и документы согласий.
- **P1 — оставшийся объём ТЗ мобильного клиента:** фото, похожие проблемы,
  уточнения и подтверждение результата, уведомления/предупреждения, профильные
  адреса и раздел дома. Реализовать до приёмки соответствующих функций.
- **Кабинет и инфраструктура:** модерация, сотрудники организаций,
  администрирование и доставка событий. Мобильный клиент не вызывает эти
  методы, но без них реальный жизненный цикл обращений не работает.

P1 не означает отказ от требований ТЗ. Разделение нужно для порядка подключения.

## 3. P0: проблемы, карта и список

| Метод | Предлагаемый путь | Доступ / результат |
| --- | --- | --- |
| GET | /v1/problems | Гость: опубликованные проблемы с пагинацией |
| GET | /v1/problems/map | Гость: маркеры или кластеры видимой области |
| GET | /v1/problems/{problem_id} | Гость: публичная карточка; с сессией — персональные флаги |
| GET | /v1/problems/{problem_id}/history | Публичная история, с пагинацией |
| POST | /v1/problems/{problem_id}/join | Пользователь: «У меня тоже», идемпотентно |
| GET | /v1/me/joined-problems | Пользователь: поддержанные проблемы |

**Фильтры списка и карты:** city_code, category_code, открытые/решённые,
период created_from/created_to, bbox или точка+радиус, поиск q.
Для карты дополнительно zoom; для списка cursor/limit и согласованный порядок.
Карта и список применяют одинаковые фильтры. Ответ карты ограничен по объёму:
при большом охвате сервер возвращает кластеры, а не все проблемы города.
Кластер содержит ID/ключ, центр, bbox и count; маркер — ID, координаты,
категорию и статус. Нужны определённые единицы радиуса и порядок координат bbox.

**Публичная карточка:** id, display_number, title, description, category_code,
city_code, location {lat,lng}, address_text, published_at, created_at,
updated_at, moderation_state, workflow_state, revision, supporters_count,
назначенная организация, ожидаемый срок и обработанные media.
Для авторизованного пользователя — joined_by_me и subscribed_by_me.
Для гостя определить значения этих флагов, например false.

**История:** id, occurred_at, event_type, from_state, to_state, actor_role,
organization, public_comment, обработанные вложения результата.
Приватные комментарии и контакты исполнителей сюда не входят.
Историю можно включить в карточку вместо отдельного endpoint, если предусмотрено
получение продолжения для длинной истории.

**Присоединение:** один пользователь даёт максимум одно присоединение к одной
проблеме. Повторные/параллельные запросы возвращают актуальные joined_by_me=true
и supporters_count без повторного увеличения. Ограничение должно действовать
в БД/транзакции, а не только на кнопке клиента.

## 4. P0: подача и «Мои заявки»

| Метод | Предлагаемый путь | Доступ / результат |
| --- | --- | --- |
| POST | /v1/reports | Авторизованный пользователь: создать обращение |
| GET | /v1/me/reports | Собственные обращения, включая непубличные |
| GET | /v1/me/reports/{report_id} | Собственная полная карточка и причины модерации |
| GET | /v1/me/reports/{report_id}/history | Доступная автору история |
| GET | /v1/me/reports/by-client-request/{client_request_id} | Найти результат отправки после таймаута |

Предлагаемый запрос создания с заголовком `Idempotency-Key`:

```json
{
  "client_request_id": "88c2032d-a38c-4f08-905c-a4111e7178e1",
  "city_code": "astana",
  "category_code": "roads.pothole",
  "title": "Яма на дороге",
  "description": "На проезжей части появилась глубокая яма.",
  "location": {"lat": 51.13, "lng": 71.43},
  "address_text": "Астана, адрес или ориентир",
  "location_confirmed": true,
  "media_ids": [],
  "publication_confirmed": true
}
```

ТЗ API-01 использует city_id/category_id, а текущие справочники возвращают code.
В примере предложены code для совместимости с ними. Нужно выбрать один контракт:
либо code, либо добавить ID в справочники. Клиент не должен угадывать соответствие.
Название publication_confirmed взято из ТЗ; publication_consent допустимо вместо
него после согласования. Подтверждение места также нужно согласовать явно.

**Валидация сервера:**

- Категория существует, активна и разрешена в выбранном городе.
- Description после trim: 10–2000 Unicode-символов; согласовать подсчёт с клиентом.
- Title до 120 символов; при отсутствии можно сформировать из описания.
- Location — конечные координаты WGS84, lat [-90,90], lng [-180,180], внутри доступного города.
- Адрес/ориентир и подтверждённая точка обязательны; свободный текст не заменяет точку.
- Publication confirmation — отдельное явное согласие, не processing/gov_transfer/push.
- Фото необязательны; до пяти принадлежащих автору доступных media_ids.
- Author ID берётся из сессии. Статусы, права и номер назначает сервер.

**Ответ 201:** id, display_number, client_request_id, moderation_state,
workflow_state, created_at, revision и problem_id, если публичная проблема уже
существует. Иначе problem_id=null. Сохранённое обращение на этом шаге означает
«Принято приложением», а не доставку или принятие организацией.

**Идемпотентность:** стабильные client_request_id и Idempotency-Key сохраняются
на клиенте до результата. После таймаута клиент сначала ищет обращение по
client_request_id, затем при необходимости повторяет запрос с тем же ключом.
Одинаковая полезная нагрузка возвращает исходный объект; другая с тем же ключом
даёт 409. Это должно работать при параллельных запросах. Указать срок хранения
ключей и контракт ответа, пока первая отправка ещё выполняется.

**Доступ:** до модерации обращение доступно только автору и уполномоченным
сотрудникам. Оно отсутствует в публичной карте, списке, поиске и выдаче медиа.
Приватная карточка содержит причины отклонения/уточнения и связь с problem_id
после публикации/объединения. Чужой report нельзя получить подбором UUID.

Обращение автора и публичная проблема могут быть разными объектами. Просьба
зафиксировать связь report_id → problem_id, включая объединение дублей.
Если в backend используется incident_id, согласуем это название как каноническое.

## 6. P1: фото и медиа

| Метод | Предлагаемый путь | Назначение |
| --- | --- | --- |
| POST | /v1/media/uploads | Создать загрузку: client_media_id, имя, MIME, размер; вернуть media_id и URL/метод загрузки |
| GET | /v1/media/{media_id} | Статус загрузки, проверки и обработки; доступный владельцу preview |
| DELETE | /v1/media/{media_id} | Удалить собственное неиспользуемое вложение |

Можно использовать один multipart endpoint вместо presigned upload: нужен
полный контракт загрузки, подтверждения завершения и повторов без дублей.
JPG/PNG/HEIC, до 10 МБ на исходный файл, до 5 фото на обращение. Проверять
реальный MIME, декодирование, размер и принадлежность медиа сервером.
Нужно согласовать ограничения пикселей, таймауты и срок действия upload URL.

Оригиналы приватны. Публично выдаётся только одобренная обработанная копия:
без EXIF/геометок, с обработкой персональных идентификаторов и модерацией.
Статусы обработки, причины отказа и временные preview URL доступны только
пользователям с правами. Загрузка фото не делает его публичным автоматически.

## 7. P1: уточнение, результат, жалобы и подписки

| Метод | Предлагаемый путь | Назначение |
| --- | --- | --- |
| POST | /v1/me/reports/{report_id}/clarifications | Ответ автора на запрос уточнения: текст, media_ids, expected_revision |
| POST | /v1/problems/{problem_id}/feedback | Подтверждение результата или «Проблема осталась»: outcome, текст, media_ids |
| POST | /v1/problems/{problem_id}/flags | Жалоба на публикацию: reason_code, пояснение |
| PUT | /v1/me/subscriptions/problems/{problem_id} | Подписаться на обновления, идемпотентно |
| DELETE | /v1/me/subscriptions/problems/{problem_id} | Отписаться, идемпотентно |
| GET | /v1/me/subscriptions/problems | Список подписок с пагинацией |

Нужны справочники outcome/reason_code, правила доступа, повторной подачи и лимиты.
«Проблема осталась» создаёт запрос модератору, а не автоматически переоткрывает
проблему. Присоединение и подписка — разные действия; если join создаёт подписку,
это должно быть явно описано, отписка не должна уменьшать счётчик поддержки.
Общий публичный чат/комментарии не требуются для текущего сценария: обязательны
комментарии истории, уточнения и обратная связь по результату.

## 8. P1: профиль, адреса и push-устройства

Текущие /me и /me/places уже есть, но их схема пока покрывает не все поля ТЗ.

| Метод | Предлагаемый путь / расширение | Назначение |
| --- | --- | --- |
| PATCH | /v1/me | Добавить изменение выбранного города через согласованный city_code/ID |
| PATCH | /v1/me/places/{place_id} | Редактирование места и его адресной подписки |
| GET | /v1/me/notification-settings | Настройки групп, тихого времени и срочных исключений |
| PUT | /v1/me/notification-settings | Сохранить настройки |
| DELETE | /v1/me/devices | Отвязать текущий push-токен; идентификатор в теле, не в URL |

Для места нужны: собственное название, тип home/work/other, город, address_text,
location, уведомления enabled и radius_m. По ТЗ — до пяти приватных адресов;
лимит проверяется сервером. Существующие label/location/radius_m сохраняем
совместимыми либо вводим новую версию схемы. Адреса никогда не попадают в публичные DTO.

При выходе сервер отзывает сессию устройства и его связь с push-токеном.
Если текущий logout принимает только refresh_token, backend должен иметь
однозначную связь session ↔ device либо нужно расширить согласованный контракт.
Определить ротацию push-токена и перенос токена между аккаунтами без доставки
прежнему владельцу. Для DELETE предложена body-схема, чтобы токен не попадал в URL-логи.

## 9. P1: уведомления и городские предупреждения

| Метод | Предлагаемый путь | Назначение |
| --- | --- | --- |
| GET | /v1/me/notifications | Лента пользователя с cursor/limit |
| GET | /v1/me/notifications/unread-count | Серверный счётчик непрочитанных |
| PUT | /v1/me/notifications/{notification_id}/read | Прочитать одно, идемпотентно |
| POST | /v1/me/notifications/read-all | Прочитать все до переданного cutoff/курсора, не затрагивая новые события |
| GET | /v1/alerts | Активные публичные предупреждения по городу/области/времени |
| GET | /v1/alerts/{alert_id} | Полная карточка предупреждения |
| GET | /v1/alerts/{alert_id}/history | Исправления и отмена предупреждения |

Уведомление: id, type, created_at, read_at, безопасные title/body,
target {type,id}, updated_at. Ответ чтения возвращает актуальный unread_count.
Push содержит event_id/notification_id, тип и ID объекта, безопасный текст и
актуальный badge. Доставка не означает прочтение. Удалённый/недоступный target
обрабатывается понятным кодом, клиент возвращается в ленту.

Предупреждение: id, тип, title/body ru/kk, источник, source_url, starts_at,
ends_at, published_at, updated_at, status, GeoJSON polygon или house_ids,
revision. Отмена и исправления сохраняют историю. Несколько адресов одного
пользователя не создают несколько доставок одного события на одно устройство.
Отказ от системного push не отключает ленту. Тихое время настраивается пользователем;
22:00–08:00 — предложенное значение ТЗ, срочные исключения согласуются отдельно.

| POST | /v1/me/house-requests/{request_id}/clarifications | Ответ автора на уточнение |

Дом: id, city, address, location, organization, проверенные рабочие контакты,
приёмные часы, updated_at. Membership: id, house_id, state, роль, даты.
Нужны ошибки для истёкшего приглашения и уже существующего участия.
Несколько домов доступны независимо; активный дом можно хранить на клиенте.

Заявка ОСИ: client_request_id, категория, описание, location внутри дома
(подъезд/этаж/общее помещение), media_ids, при необходимости приватные контакты.
Номера квартир и контакты видят только уполномоченные обработчики.
Заявка не попадает на городскую карту. Участие в доме не подтверждает собственность.
До подтверждения участия доступны только публичные сведения дома.
Закрытые новости — подтверждённым участникам; приватные заявки — автору и
уполномоченным сотрудникам, а не всем соседям.
Перевод в публичную проблему требует решения модератора и согласия автора,
очистки персональных данных и истории преобразования.

## 11. Кабинет модератора и организации

Это отдельные API с серверной проверкой роли/города/организации. Пути примерные;
для мобилки важны результирующие статусы и события, а не конкретные названия.

| Метод | Предлагаемый путь | Назначение |
| --- | --- | --- |
| GET | /v1/staff/reports | Очередь: фильтры город/организация/категория/состояние/период/просрочка/дубль |
| GET | /v1/staff/reports/{report_id} | Карточка с разрешёнными приватными полями |
| POST | /v1/staff/reports/{report_id}/actions | publish, request_clarification, reject, hide, merge, assign; причина и expected_revision |
| POST | /v1/staff/problems/{problem_id}/actions | accept, reject_assignment, start_work, set_due_date, resolve; expected_revision |
| GET | /v1/staff/houses/{house_id}/membership-requests | Очередь вступления |
| POST | /v1/staff/house-membership-requests/{id}/decisions | Подтвердить/отклонить вступление |
| POST | /v1/staff/houses/{house_id}/invitations | Создать адресное приглашение |
| GET | /v1/staff/house-requests | Приватная очередь ОСИ в пределах прав |
| POST | /v1/staff/house-requests/{id}/actions | Уточнение, работа, результат, запрос на публичное преобразование |
| POST/PATCH | /v1/staff/houses/{house_id}/news[/{news_id}] | Создать/исправить новость |
| POST | /v1/staff/houses/{house_id}/news/{news_id}/unpublish | Снять новость, с причиной и аудитом |
| POST/PATCH | /v1/staff/alerts[/{alert_id}] | Подготовить/исправить предупреждение |
| POST | /v1/staff/alerts/{alert_id}/preview | Территория, предполагаемые получатели, предпросмотр |
| POST | /v1/staff/alerts/{alert_id}/publish | Подтвердить рассылку с отдельным правом |
| POST | /v1/staff/alerts/{alert_id}/cancel | Отменить предупреждение и уведомить получателей |

В строках POST/PATCH квадратные скобки обозначают два пути: POST коллекции и
PATCH объекта; это не буквальная часть URL. Вместо actions допустимы отдельные
endpoints каждого действия; нужен полный перечень payload и прав в Swagger.

Для админки нужны управление категориями и их ru/kk, городами/границами,
организациями/зонами маршрутизации, домами, сотрудниками/ролями, блокировками
пользователей и восстановлением доступа. Предлагаемые ресурсы под `/v1/admin/`:
categories, cities, organizations, routing-zones, houses, staff, user-restrictions.
Для каждого — разрешённые list/detail/create/update/deactivate или delete,
revision и аудит. Точный набор административных действий согласовать с кабинетом.
Отдельное чтение audit-events разрешается только соответствующей роли;
изменение/удаление аудита через обычный кабинет запрещено.

**Правила жизненного цикла:**

- Раздельные moderation_state и workflow_state; перечень кодов и матрица переходов.
- Каждое изменение с expected_revision/If-Match; конфликт 409 с актуальным состоянием.
- Статус, событие истории и событие для уведомления фиксируются атомарно.
- «Передано» только после подтверждённой доставки, «Принято организацией» — после её подтверждения.
- Для resolve — комментарий и обработанное фото результата либо разрешённое модератором исключение с причиной.
- Срок организации и внешней процедуры различаются; универсальные 15 дней не задаются для всех проблем.
- Дубликаты объединяются без потери истории и повторного учёта одного пользователя.
- Отзыв роли/доступа сотрудника закрывает сессии; общие аккаунты сотрудников не используются.

## 12. Общий контракт для всех методов

1. JSON, `/v1`, `Accept-Language: ru|kk`, Bearer на защищённых методах.
   Гостевой публичный доступ сохраняется; персональные флаги вычисляются из сессии.
2. Даты ISO 8601 с timezone, предпочтительно UTC; координаты WGS84.
   Пользовательский контент сохраняется на языке автора, справочники локализуются.
3. UUID/ID и display_number имеют разные назначения. Отдельно описать nullable поля.
4. Пагинация: items, next_cursor, has_more; предложенный limit 20, максимум 100.
   Стабильный порядок, например timestamp+id. Map aggregates имеют отдельный лимит.
5. Ошибки 400/401/403/404/409/422/429/503: code, message, field_errors,
   trace_id, retry_after при необходимости. 429 также содержит Retry-After.
   В текущем API 422 — FastAPI detail[]: сохранить совместимость либо согласовать переход.
6. Документировать ограничения OTP, попыток, загрузок, подач, присоединений и жалоб.
   По ТЗ предложены OTP 5 мин/5 попыток/повтор 60 сек и 10 подач в сутки;
   это параметры для согласования, а не подтверждённые текущие настройки сервера.
7. Публичный автор — псевдоним или «Житель». Нет телефонов, квартир, адресов профиля,
   приватных комментариев, приглашений и исходных фото в публичных ответах.
8. Подписанные приватные URL ограничены сроком/правами. Снятая публикация исключается
   из публичных методов и медиа; определить поведение кеша и удаления файлов.
9. OpenAPI включает request/response DTO, security, фильтры, все ошибки и примеры.
   Изменения схем совместимы с поддерживаемыми клиентами; правила обязательного
   обновления возвращаются через согласованное расширение /v1/meta.
10. Локальный черновик текущего этапа не требует серверного endpoint.
    Фоновая отправка после восстановления сети не выполняется.

## 13. Что предоставить для интеграции и приёмки

- Обновлённый OpenAPI и таблицу соответствия предложенных путей реальным.
- Staging URL, доступ с Android/iOS через сеть/VPN; production HTTPS URL.
- Тестовый номер и безопасный способ получения OTP на staging; не production bypass.
- Тестовые роли: житель, модератор, сотрудник организации, администратор ОСИ.
- Данные: город с границей, категории, опубликованные/решённые проблемы,
  непроверенное и отклонённое обращение, запрос уточнения, объединённый дубль,
  дом/приглашение, приватная заявка, предупреждение, непрочитанные уведомления.
- Firebase/APNs конфигурацию клиента, согласованный push payload и тестовую доставку.
  Секреты серверных провайдеров передавать защищённо, не в репозитории/мобильном коде.
- Версии юридических текстов ru/kk, политику удаления и хранения данных/медиа.
- Кто выполняет модерацию, куда маршрутизируются обращения, как подтверждается доставка.
- Серверные фоновые процессы медиа/уведомлений и надёжный outbox или эквивалент:
  повтор задач не создаёт дублей. Персональные данные/приватное хранилище/бэкапы
  размещаются согласно проектному требованию ТЗ в Казахстане; правовые детали
  и внешние передачи согласуются отдельно до пилота.

## 14. Сценарии приёмки P0

1. Гость видит только опубликованные проблемы; одинаковые фильтры на карте и в списке.
2. Автор создаёт обращение и видит его в своих заявках; другой житель и гость не видят его до модерации.
3. Таймаут отправки → поиск по client_request_id → тот же объект, без дубля.
4. Параллельная подача с одним ключом даёт один объект; изменённые данные дают 409.
5. Повторное/параллельное «У меня тоже» увеличивает счётчик ровно один раз.
6. Модератор публикует → публичная карточка/карта обновляются, автор видит связь с проблемой.
7. Организация принимает/работает/решает → статусы, история и уведомления согласованы.
8. Чужие приватные UUID и дом без членства не раскрывают данные.
9. Устаревшая revision, исчерпанный лимит и недействительная сессия имеют документированные ответы.
10. Полные согласия доступны до входа; добровольные и публикационные согласия не подменяются обязательным processing.

В первую очередь просим оценку сроков для P0 и согласованные DTO создания,
карточки, списков, идемпотентности и присоединения. Затем подключим реальные
обращения в приложении и последовательно оставшиеся разделы P1.
